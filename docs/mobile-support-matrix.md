# Mobile support matrix

Keep the mobile host in `kui-native` and qualify phones first. Set the iPhone deployment floor to **iOS 17.0** and keep **Android 9 / API 28**. iOS 17 lets the release use the same VoiceOver announcement priority API on every supported iPhone and keeps the A12 iPhone XR and XS in scope. On Android, start with 64-bit ARM and require a Vulkan or GLES adapter that can initialize the KUI renderer. Keep x86_64 as a CI emulator target.

## Runner, Kit and packs

Ship a **signed app per Lua project** first. Build the existing source `.kui` archive with `kui pack`, embed it as an iOS resource or Android asset, then package and sign the app with the platform toolchain. Use the project's reverse-DNS ID for the bundle or application ID and its private data namespace. The update goes through the same distribution channel as the app. Treat a general-purpose runner that installs executable packs after launch as a separate product decision subject to the platform rules below.

| Responsibility | Mobile design |
| --- | --- |
| App runner | Share the project entry, manifest and version checks, module loading, Lua lifecycle and frame work already exercised by desktop. Put the bundle reader and app initialization behind an entry point that receives the pack, data paths and scheduler from the host. Start from `host::load_app` and `packed::from_file`. The desktop CLI keeps its command parsing, file watching and menus. |
| Platform host | Invoke the existing `kui-native::mobile::run` entry point and wake the app through its UI loop. Native owns touch, keyboard, insets, accessibility, rendering and lifecycle. Web uses its existing browser adapters and shares KUI core interactions, Lua app semantics and Kit source. |
| Kit | Link `kui-kit` and reuse the same embedded Lua component definitions as desktop and web. Rust apps can use the existing typed builders. Lua apps keep `require("kit.ui")`. Exercise the button, text field, checkbox, scroll list and focus traversal before extending the first app's component coverage. |
| Pack and data | Reuse `kui.pack.lua`, the archive path rules and project ID. If the current image and font readers need real paths, reuse the hash-keyed extraction into app-private cache. Expose the extracted assets as read-only to scripts and keep mutable data in `kui.data_dir`, independent of the installed pack hash. Use source archives for the first pass. Keep `--format web` and its existing browser bundle. |
| Host APIs | Start with the APIs the first app needs. Give file access to the bundled assets and app data, then reuse JSON, time and task dispatch. Document host capabilities by target. |

Bundle reusable Lua components and themes as project modules at build time. That gives a shared component the same review and versioning as the rest of the project. Keep separately downloaded content packs declarative, with the app interpreting their data through its existing features.

Use the existing Tasks tutorial for the first packaged app. It already uses Kit and persists JSON through `kui.data_dir`. Build it for desktop, the browser and the two phone hosts from one project, then create, check and clear tasks by touch. Enter text with the native keyboards, scroll a long list and verify that tasks survive a cold relaunch and an app update. Use Field Notes for the later SQLite and iPad scene test. It adds asynchronous saves and would exercise shared data with independent window state. [Tasks tutorial](../examples/lua/tutorial/tasks/main.lua) · [Runner ADR](adr/0064-the-kui-runner.md) · [Pack ADR](adr/0068-how-kui-reaches-a-machine.md) · [Kit bindings](../addons/kit/bindings/rust/src/lib.rs) · [Field Notes](../addons/kit/samples/field-notes/README.md)

## Platform constraints and sources

### iOS

- Use `aarch64-apple-ios` for devices and `aarch64-apple-ios-sim` for Simulator on Apple silicon. Rust uses the corresponding Xcode SDK and respects `IPHONEOS_DEPLOYMENT_TARGET`. Xcode 27.2 ships the iOS 27.2 SDK and accepts deployment targets from iOS 15 through 27. Its supported simulators and on-device debugging start at iOS 17. For App Store Connect uploads, Apple currently requires Xcode 26 or later and an iOS 26 SDK or later. [Rust iOS targets](https://doc.rust-lang.org/rustc/platform-support/apple-ios.html) · [Xcode support matrix](https://developer.apple.com/xcode/system-requirements/) · [App Store Connect SDK requirement](https://developer.apple.com/news/upcoming-requirements/?id=04282026a)
- For an iOS 17.0 runtime check, open Xcode **Settings → Components → Add Platforms** or use `xcodebuild -downloadPlatform iOS -buildVersion 17.0`. Apple lists stable iOS 17.0 (21A328) and 17.5 (21F79) images. Its 16.x downloads list macOS and Xcode 26.99.0 as the maximum, which rules out the macOS 27 and Xcode 27 host. Xcode 26.6 on macOS Tahoe 26.2–26.x is a supported setup for iOS 16 simulation and on-device debugging. [Xcode component downloads](https://developer.apple.com/documentation/xcode/downloading-and-installing-additional-xcode-components) · [Apple runtime catalog](https://devimages-cdn.apple.com/downloads/xcode/simulators/index2.dvtdownloadableindex) · [Xcode support matrix](https://developer.apple.com/xcode/system-requirements/)
- Moving the floor from iOS 16 to 17 drops the A11 iPhone 8, 8 Plus and X. The iPhone XR, XS and XS Max are A12 devices that can run iOS 17. Both GPU generations support Metal. Simulator translates Metal calls to the Mac GPU, so use a physical phone to check the selected GPU and driver. [Apple OS compatibility by release](https://support.apple.com/en-us/100100) · [A11 graphics processors](https://developer.apple.com/library/archive/documentation/DeviceInformation/Reference/iOSDeviceCompatibility/HardwareGPUInformation/HardwareGPUInformation.html) · [iPhone XR specifications](https://support.apple.com/en-us/111868) · [iPhone XS and XS Max specifications](https://www.apple.com/newsroom/2018/09/iphone-xs-and-iphone-xs-max-bring-the-best-and-biggest-displays-to-iphone/) · [Metal GPU families](https://developer.apple.com/documentation/metal/mtlfeatureset) · [Metal in Simulator](https://developer.apple.com/documentation/metal/developing-metal-apps-that-run-in-simulator)
- UIKit introduced `UIKeyboardLayoutGuide` in iOS 15. It tracks the docked keyboard by default. The host uses announcement priorities from iOS 17 and falls back to UIKit's queue attribute on iOS 16, so VoiceOver feedback needs a run on whichever path the app declares. [UIKit keyboard layout guide](https://developer.apple.com/videos/play/wwdc2023/10281/) · [Announcement priorities](https://developer.apple.com/documentation/uikit/uiaccessibilitypriority) · [Host announcement code](../crates/kui-native/ios/accessibility.m)

### Android

- Android 9 is API 28. An ARM64 release uses Rust's `aarch64-linux-android` target and needs the device to report `arm64-v8a` among its supported ABIs. Android 9 permits several ABIs. Set `minSdk` and the native linker target to API 28 for this floor. Google Play's current requirement for new phone apps and updates is `targetSdk` 36 or higher. [Android 9 APIs](https://developer.android.com/about/versions/pie/android-9.0) · [Rust Android targets](https://doc.rust-lang.org/rustc/platform-support/android.html) · [Android 9 compatibility definition](https://source.android.com/docs/compatibility/9/android-9-cdd) · [NDK SDK version properties](https://developer.android.com/ndk/guides/sdk-versions) · [Play target SDK requirements](https://developer.android.com/google/play/requirements/target-sdk)
- Android 9 permits devices without Vulkan and without OpenGL ES 3.x. Confirm that a physical device exposes a compatible Vulkan or GLES adapter and that KUI renders with it. [Android 9 graphics requirements](https://source.android.com/docs/compatibility/9/android-9-cdd#7_1_4_2d_and_3d_graphics_acceleration)
- The public NDK font matcher and system font iterator begin at API 29. The sample weak-links the font symbols, checks the API level, and on API 28 reads the Japanese face from the system font XML. That fallback depends on the device's font configuration. Verify the intended glyphs on API 28 hardware or supply a bundled fallback face. [NDK font API](https://developer.android.com/ndk/reference/group/font) · [NDK weak references](https://developer.android.com/ndk/guides/using-newer-apis) · [AOSP Android 9 font configuration](https://android.googlesource.com/platform/frameworks/base/+/android-9.0.0_r1/data/fonts/fonts.xml) · [Sample font selection](../examples/rust/apps/mobile/src/fonts.rs)

### Executable packs

- Packaging the interpreter and first-party Lua/Kit packs with the signed app puts that code in the build submitted for review. Apple's App Review Guideline 2.5.2 restricts downloaded code that adds or changes functionality. Guideline 4.7 covers specified categories of hosted software and requires prior permission to expose native platform APIs. The Developer Program License Agreement also conditions interpreted downloads on retaining the app's primary purpose, respecting platform security and avoiding an app storefront. [App Review Guidelines §§2.5.2 and 4.7](https://developer.apple.com/app-store/review/guidelines/) · [Developer Program License Agreement §3.3.1](https://developer.apple.com/support/terms/apple-developer-program-license-agreement/)
- Google Play requires updates through Play and restricts off-Play downloads of executables such as DEX, JAR and native libraries. Its interpreter exception addresses indirect access to Android APIs. Google explicitly includes Lua among runtime-loaded interpreted code that must be constrained so it cannot enable Play policy violations. Assess future remotely supplied executable packs against both stores' rules for the host APIs they can invoke. [Google Play Device and Network Abuse policy](https://support.google.com/googleplay/android-developer/answer/16559646)
