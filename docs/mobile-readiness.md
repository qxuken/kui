# Mobile readiness for kui-native

The first release target is a single-window Rust app that someone can install on an iPhone and an Android phone, navigate by touch or screen reader, type into, and return to after an interruption. Keep one Rust app and the mobile host in `kui-native`. Use the existing activation, scroll and text events. The native host and both web canvas renderers share release-velocity sampling and momentum integration in kui-core. Each host translates platform input and routes unconsumed scrolling. Revisit the public event API when a concrete interaction cannot be expressed through it.

### iPhone 15 Pro, iOS 27.2.1

- The signed single-window spike ran on Metal. All 12 flicks starting on Increment scrolled with zero clicks, including six that also ended inside the button. A separate tap incremented once.
- Bottom note rose above the Apple software keyboard and accepted a letter in portrait, another in landscape, and a third after returning to portrait. Dismissing the keyboard restored the list height. The draft survived both a same-process resume and a cold relaunch.
- The UIKit two-field regression produced `aéb` with the caret before `b`. It finished at `aé!Zb` with caret byte 5, the second field unchanged, and exactly three model changes.
- Starting at `say d|rain now`, the English (UK) software keyboard corrected the inserted `dont` to `don’t` on Space. The caret was at byte 14 before `rain`, and typing `x` advanced it to byte 15. Japanese Romaji rendered marked `にほん` in the field. Choosing `日本` from the candidate bar rendered both kanji and committed `say d日本|rain now` at byte 11. Switching back to English and typing `x` produced `say d日本x|rain now` at byte 12.
- With VoiceOver, the listener heard Increment and Note, activated the button, and used a three-finger swipe with the keyboard closed to reach Bottom note. Activating the field opened the Apple keyboard and typing changed the bottom draft.
- Before the announcement fix, the count changed and UIKit reported a successful announcement while the listener heard no automatic count. The VoiceOver Caption Panel showed that a reread of Increment could replace the queued count. The iOS host now submits one-off speech after AccessKit's tree events, and the spike gives the deliberate activation's confirmation high priority. On the signed build, the panel showed “Button taps: 1” in three fresh launches. The listener then heard “Button taps: 2” after activating Increment without selecting the count.

### Navigation and gesture interruption

- The shared navigation trial ran on the iPhone 15 Pro and Galaxy S24 Ultra. On iPhone, Hide keyboard, Close editor and Back closed one layer at a time. On Galaxy, both Back key events and the system edge gesture closed the keyboard, modal and detail in order.
- Both devices resumed the open editor in the same process, accepted another software-keyboard character, and showed the complete draft after a cold launch.
- A slider drag changed the value while both scroll offsets stayed at zero. The first swipe inside the inner list moved it to its limit while the outer list stayed fixed. The next swipe from inside that list moved the outer list.
- Backgrounding during a pending press produced zero taps, and a fresh tap produced one. On iPhone, the native trace recorded the touch start followed by suspension before release. An interrupted slider drag settled at 43 on iPhone and 57 on Galaxy, and both values stayed stable until the next drag.

The phone preview, navigation and gesture-interruption hardware checks and the iPad window-restoration checks are complete. The support matrix sets iOS 17.0 and Android 9 / API 28 as the phone floors. Release qualification still needs the exact iOS 17.0 runtime, the oldest supported physical devices and signed release builds. The iPad rename and independent navigation scenario still needs an implementation and a device run. [Support matrix and packaged runner plan](mobile-support-matrix.md)

The early `か` commit came from the test setup. With a deliberate 600 ms delay before the focus switch, the Galaxy trace showed the bridge publish the marked range and Gboard call `finishComposingText` on the active connection about 210 ms later. The same delayed build failed four times with Gboard and passed four times with the test keyboard. The updated runner gives the probe control of composition on Android's real input connection. The production bridge and its assertions are unchanged. The Android 15 emulator also passed five cold launches. The 11 native touch unit tests passed locally.

On Android, the native input queue receives hover events before the Java view hierarchy. Upstream winit 0.30.13 marks them handled without delivering them. The mobile feature selects `kui-winit`, which lets the three hover actions reach the AccessKit delegate. It also initializes iOS windows in the selected UIKit scene.

The initial scope is phones, a docked keyboard, one foreground window and bundled Rust app assets. iPad multi-window follows the phone release as milestone 6. Independent simultaneous gestures and a packaged Kit/Lua host can be planned against specific app requirements.

## 6. Open two notes side by side on iPad

The opt-in iPad example opens a UIKit scene session for each window. Each has a KUI core, render surface, touch state, accessibility adapter and native editor. The scene factory shares the font session and note store across windows. The phone example continues to use the single-window entry point.

On the 13-inch iPad Pro simulator, A and B were arranged side by side. Alternating edits were saved in their intended drafts. Scrolling B left A stationary, and resizing A changed its visible paragraph count independently. After A closed, B accepted another edit at its existing scroll position. Reopening A showed its saved text. After SIGKILL and relaunch, both original sessions returned side by side. The simulator check compares a rendered paragraph’s screen coordinates in each window, then types at each restored caret and verifies both draft contents. Repeating the relaunch after closing B, and again after closing A, brought back only the surviving window at its previous scroll position and caret. [Run the tablet check](../examples/rust/apps/mobile/README.md#ipad-windows)

Both cold-launch scenarios also passed on an iPad mini (A17 Pro) running iPadOS 27.0.1 with the software keyboard visible before termination. In the first two-window run, Note A restored paragraph 5 and the caret after character 2. Note B restored paragraph 14 and the caret after character 5. Paragraphs returned within one point relative to the field even when iPadOS moved a window. In the close-and-relaunch runs, only the original surviving scene returned. Typing without tapping the field produced `Draftz B` after A was closed and `Drqaft A` after B was closed. Both probe characters were removed. The injected window-switch shortcut did not reliably transfer keyboard input between the two open windows on this device. Note B’s caret was checked visually in the two-window run and by typing in the one-window run.

| Owner | State and responsibility |
| --- | --- |
| App process | One note store keyed by stable note ID owns titles, committed edits, drafts and saves. Both windows read from it. A title change appears wherever that note is listed. App preferences and immutable assets such as bundled fonts are also shared. |
| Each window | Its scene session identifies a KUI core, navigation stack and current note ID. That window owns field focus, caret and selection, pending keyboard composition, scroll position, accessibility tree, viewport, safe area, keyboard insets and rendering surface. Store the note ID and restorable view state under the scene session ID. Disconnecting one scene releases its surface and input connections. |

### Acceptance check

Run this scenario first on an iPad simulator, then on a physical iPad with the software keyboard.

1. Seed two long notes, A and B, with distinguishable text and numbered paragraphs. Open A, choose **Open in New Window** for B, and arrange the two app windows side by side. Check that each shows its requested note.
2. In A, scroll to paragraph 3 and place the caret after a known word. In B, scroll to paragraph 12 and replace a selected word. Return keyboard focus to A and type at its saved caret. Verify the exact text in both notes, each window’s scroll marker, and that each edit landed once.
3. Rename B in its window. Open the note list in A’s window and verify the new title appears there. Navigate back to A and verify its draft and reading position. This checks shared document data and independent navigation in the same run.
4. With B editing, resize the windows. Check that each lays out to its own bounds and B’s caret remains visible. Close A’s window, then type another word in B at its existing caret. Reopen A in a new window and verify its saved text and B’s continued scroll position.
5. Put the two windows at different paragraphs and caret positions. Kill the process and relaunch it. Verify both windows return together, each paragraph is in its previous screen position, and typing without retapping either field inserts at its saved caret.
6. Close one window using the red system window control. Kill and relaunch the app with just the other window open. Verify the closed window stays closed, compare the surviving window’s paragraph position, and type without tapping its field to check the saved caret. Repeat with the other note as the surviving window.

The iPad milestone passes when both devices complete the scenario and the existing single-window iPhone smoke tests still pass. Record the scene session ID, note ID and active keyboard target on failure so an edit routed to the wrong window can be traced.
